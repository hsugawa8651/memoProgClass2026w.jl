第11回：復習

今回は 予備・復習回 である．新しいことは学ばない． 第1〜10回で出会った 衝撃的な「落とし穴の例」 をいくつか選び， AIに頼らず，自分のことばで「なぜそうなるか」を説明できるか を確かめる．

重要この回のねらい（評価との接続）

ここで再掲する例は，どれも「結果が直感に反する」が，理由は これまで学んだ概念だけ で説明できる． 口頭試問や小テストでは，AIなしで これらを説明してもらう． だから今回は，各例を「予測 → 実行 → なぜ？」の順に，自分のことばで言い切る練習をする．

各節は次の形で進める．

  1. 予測：実行する前に，結果を Markdown セルに書く（提出物に予測が残る）．
  2. 実行：セルを動かして照合する（予測が外れたら，それが学びの種）．
  3. なぜ？：理由を 一文 で言う．該当回を見直す．

落とし穴の例1：0.1 + 0.2 と 0.3 を == で比べる

重要予測 → 実行 → なぜ？（第6回）

0.1 + 0.2 == 0.3 は true か false か？　まず予測しよう．

0.1 + 0.2 == 0.3
false
0.1 + 0.2          # look at the last digits
0.30000000000000004
警告落とし穴：足し算が「ぴったり」にならない

0.1 + 0.2 は 0.3 ではなく 0.30000000000000004 になる． だから == は false を返す．

ノートなぜ？（→ 第6回）

コンピュータは数を 2進法・有限の有効数字 で持つ． 0.1 や 0.2 は2進法では 割り切れない無限小数 なので，途中で打ち切った近似値が入る． 近似どうしを足すと，0.3 の近似値とはわずかにずれる． だから小数の比較に == は使わない． 第10回で学んだとおり，≈（isapprox） を使うか， 差の大きさ abs(a - b) が十分小さいかを調べる．

落とし穴の例2：Int8 の最大値に 1 を足す

重要予測 → 実行 → なぜ？（第9回）

Int8（8ビット整数）で 127 + 1 はいくつになるか．

Int8(127) + Int8(1)     # what does the sum become?
-128

bitstring でビットの並びを見ると，仕組みが見える．

bitstring(Int8(127))    # 01111111
"01111111"
bitstring(Int8(-128))   # 10000000
"10000000"
警告落とし穴：最大値の次が最小値

Int8 は \(-128\) 〜 \(127\) しか表せない．127 に 1 を足すと 一周して -128 に戻る．

ノートなぜ？（→ 第9回）

Int8 は 8ビットしかない有限の入れ物で，値は 2の補数 で表す． 127 = 01111111 に 1 を足すと 10000000 になり，これは2の補数では -128． 桁あふれ（オーバーフロー）が エラーにならず，黙って一周する のが怖いところ． 大きな整数を扱うときは，このことを忘れない（第9回の myfactorial(21) が負になるのも同じ理由）．

落とし穴の例3：b = a のあとに a を書き換える

重要予測 → 実行 → なぜ？（第8回）

a = [1, 2, 3] としてから b = a とし，そのあと a[1] = 99 とすると，b はどうなるか？ b は [1, 2, 3] のまま？　それとも変わる？

a = [1, 2, 3]
b = a            # just a second name tag on the same array
a[1] = 99        # overwrite the 1st element of a
b                # what is b now?
3-element Vector{Int64}:
 99
  2
  3
警告落とし穴：触っていない b が変わる

b には何もしていないのに b も [99, 2, 3] になる．これを aliasing（別名） という．

ノートなぜ？（→ 第1回・第8回）

b = a は「コピーを作る」のではなく，同じ配列に2枚目の名札を貼るだけ（札モデル）． だから a 経由で中身を書き換えると，同じものを指す b 経由でも変わって見える． 中身を独立させたいときは b = copy(a) とする． スカラー（第1回の r = q）では差が見えなかったが，配列では効いてくる．

落とし穴の例4：(1e16 + 1) - 1e16 を計算する

重要予測 → 実行 → なぜ？（第10回）

(1e16 + 1) - 1e16 はいくつか？　数学なら当然 1 のはずだが…．

(1e16 + 1) - 1e16       # math says 1.0; what does Julia say?
0.0
1e16 + 1                # and what is this?
1.0e16
警告落とし穴：足したはずの 1 が消える

1e16 + 1 の時点で 1 が反映されず，差を取ると 0.0 になる．

ノートなぜ？（→ 第10回）

浮動小数点数の有効数字は約16桁．1e16（=\(10^{16}\)）と 1 は 桁が違いすぎて， 1e16 + 1 を16桁に丸めると 1 の分は表現しきれず 消える（情報落ち）． 桁の大きく違う数の足し引きでは，小さい方が失われることがある． なお，ほぼ等しい数どうしの引き算で有効数字が失われるのは別の現象で，桁落ち という．

今回のまとめ

  • 0.1 + 0.2 == 0.3 が false：小数は 2進・有限の有効数字 の近似．小数の == は使わない（第6回）．
  • Int8(127) + Int8(1) が -128：有限ビット・2の補数 で一周する（オーバーフロー，第9回）．
  • b = a で b も変わる：コピーではなく同じ配列の別名（aliasing・札モデル，第1回・第8回）．copy で防ぐ．
  • (1e16 + 1) - 1e16 が 0：足した時点で 1 が消えている（情報落ち，第10回）．
  • 4例の原因は別々だが，どれも 有限の入れ物で数を扱う という同じ根から来ている．
