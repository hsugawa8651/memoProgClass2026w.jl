第10回：浮動小数点と数値誤差

今回の核は，「浮動小数点は有限の有効数字である」ということに尽きる． コンピュータは小数を，仮数部が 有限のビットしかない形で記憶する． だから 表せない数は丸められ，計算の途中で 桁が落ちる． 第9回で学んだ「整数＝有限のビットの世界（2の補数）」と対をなす， もう一方の真実（計算機の数 ≠ 数学の数）が，ここで姿を現す．

そして今回から，検証は新しい段階（L3）に入る． 「ちゃんと動くし，もっともらしいのに，答えが微妙に違う」． この厄介な状況を，厳密に分かっている値との差で暴くのが今回の道具立てである．

ノート

第6回で 0.1 + 0.2 == 0.3 が false になり，驚いた（あるいは納得できなかった）人もいるだろう． 今回はその 仕組みを説明する．「なぜそうなるのか」を言葉で言えることが目標である．

表せない数：0.1 は丸められている

0.1 という何でもない小数が，実はそのままでは記憶できない． 2進数で 0.1 を表そうとすると 無限に循環するため，有限ビットの仮数部に収めるとき 丸められる． その結果，足し算がきれいに揃わない．

重要実行する前に予測しよう（L1）

0.1 + 0.2 はいくつになるか？　また 0.1 + 0.2 == 0.3 は true か false か？

0.1 + 0.2            # look at the last digits
0.30000000000000004
0.1 + 0.2 == 0.3     # true or false?
false

「コンピュータがバグっている」のではない． 実際に 0.1 として格納されている値を，big（多倍長）で覗いてみよう．

big(0.1)             # what the Float64 0.1 "really" is
0.1000000000000000055511151231257827021181583404541015625

ちょうど 0.1 ではなく，ごくわずかにずれた数が入っている． 0.1 も 0.2 も 0.3 もそれぞれ丸められており， 丸めた結果の和と丸めた 0.3 が一致しないために == が false になる．

ノート補足：Float64 はおよそ10進15〜16桁

コースで使う標準の小数は Float64（倍精度）で，仮数部は約53ビット， 10進にして15〜16桁ぶんの有効数字しか持たない． それを超える細かさは表現できず，必ず丸められる．

桁が大きく違う数を足す

1e16 は \(10^{16}\) を表す書き方である（e のうしろが10のべき乗の指数）． この大きな数に，1 を足してみよう．

重要予測しよう（L1）

1e16 + 1 は 1e16 より大きいはずだから，1e16 + 1 == 1e16 は false ……だろうか？

1e16 + 1 == 1e16     # true or false?
true

1e16 はすでに有効数字16桁ぎりぎりで， そこへ 1 を足しても，その 1 は表現できる細かさの 外側にある． だから丸めると元の 1e16 に戻ってしまう．足したのに増えないのである． 桁が大きく違う数どうしを足すと，小さい方が有効数字の外にはみ出して消える． これを 情報落ち という．

近い数どうしを引く

今度は，ほとんど等しい2つの数を引いてみよう．

重要予測しよう（L1）

(1e16 + 1) - 1e16 はいくつか？　数学なら当然 1.0 だが……

(1e16 + 1) - 1e16    # math says 1.0; what does Julia say?
0.0

先ほどの情報落ちで 1e16 + 1 がすでに 1e16 に丸められているため， そこから 1e16 を引けば 0.0 になる． 本来あったはずの 1 の情報は，足した瞬間に失われていた．

ほとんど等しい2つの数を引くと，上位の桁がきれいに打ち消し合い， 残るのは誤差を含む下位の桁だけになる．有効数字が一気に失われるこの現象を 桁落ち という．

数値微分：小さくしすぎると悪くなる（U字）

桁落ちが現実の計算を壊す代表例が 数値微分である． 微分の定義にならって，差分商で導関数を近似する：

\[ f'(x) \approx \frac{f(x+h) - f(x)}{h} \]

理論上は \(h\) を小さくするほど近似はよくなるはずである． ところが分子 \(f(x+h) - f(x)\) は 近い数どうしの引き算＝桁落ちの巣窟であり， \(h\) を小さくしすぎると誤差はかえって 増える．

f(x) = x^2 の x = 1 での厳密値は \(f'(1) = 2\)． これを既知の正解として，さまざまな h での誤差を見比べよう． 誤差は「厳密値との差の大きさ」，すなわち \(|d - 2|\) で測る． 絶対値は abs で計算する（abs(-3) は 3）．

重要予測しよう（L1）

h をどんどん小さくしていくと，厳密値 2 との誤差はどうなるか？ ずっと減り続けるだろうか？

f(x) = x^2                       # exact value is f'(1) = 2
for h in [1e-1, 1e-4, 1e-8, 1e-12, 1e-15]
    d = (f(1+h) - f(1)) / h
    println(h, "  approx ", d, "  error ", abs(d - 2))
end
0.1  approx 2.100000000000002  error 0.10000000000000187
0.0001  approx 2.000099999999172  error 9.999999917198465e-5
1.0e-8  approx 1.999999987845058  error 1.21549419418443e-8
1.0e-12  approx 2.000177801164682  error 0.00017780116468202323
1.0e-15  approx 2.220446049250313  error 0.22044604925031308

誤差は 一旦減ってから，ある所を境に増えていく（U字になる）． 前半は近似の打ち切り誤差が減るから改善するが， 後半は分子の桁落ちが効いて，h で割ることで誤差が拡大する． 理論（改善）と実測（途中から悪化）が食い違う．これが L3 検証の典型例である．

ノート補足：これが「L3」の誕生点

コードはエラーも出さず動き，結果ももっともらしい． それでも答えはずれている． こういう誤りは「動くかどうか」では見抜けない． 厳密に分かっている値（ここでは 2）との差を取ることで，初めて姿を現す． 今後 AI が書いたコードを検証するときも，この「既知解との差」が主役になる．

正しい比較：== ではなく isapprox（≈）

浮動小数点数には必ず丸め誤差がつきまとう． だから小数を == で「ぴったり等しいか」調べるのは，ほとんどの場合 やってはいけない． 代わりに，十分近いかを調べる isapprox（演算子 ≈，\approx+TABで入力）を使う．

0.1 + 0.2 == 0.3     # exact equality
false
0.1 + 0.2 ≈ 0.3      # close enough? (isapprox)
true

≈ は isapprox の演算子版で，次の関数呼び出しと同じである．

isapprox(0.1 + 0.2, 0.3)
true
ヒント

小数の比較は == ではなく ≈（isapprox）． これが今回いちばん持ち帰ってほしい実務上の習慣である． ただし 0 との比較に ≈ は使えない（isapprox(1e-20, 0.0) は false になる）． 0 に近いかを見るときは，abs(x) < 1e-10 のように 差の大きさ で判定する． 第6回で 0.1 + 0.2 == 0.3 が false になった理由は「有限の有効数字」であり， 正しい比較の仕方が ≈ だった，というところまで繋がった．

NaN と Inf：数でない結果

浮動小数点数には，ふつうの数のほかに特別な値がある． Inf（無限大）と NaN（Not a Number，数でない）である． たとえば「正の数 ÷ 0」は Inf になる．

1.0 / 0.0            # what comes out of a division by zero?
Inf

Inf - Inf のように 答えが定まらない計算をすると NaN になる．

重要予測しよう（L1）

Inf - Inf は 0 だろうか？　また，もし結果が NaN だとして，NaN == NaN は true か？

Inf - Inf            # what comes out of infinity minus infinity?
NaN
NaN == NaN           # is NaN equal to itself?
false

NaN は「数でない」ので，自分自身とすら等しくないよう定められている． そのため x == x が false になったら，その x は NaN だと分かる． NaN かどうかを正しく調べるには専用の関数 isnan を使う．

isnan(Inf - Inf)     # use this to test for NaN
true
ノート補足：NaN は伝播する

NaN を含む計算は，たいてい結果も NaN になって広がっていく（伝播）． 計算の途中で NaN が紛れ込むと，最後の答えまで NaN に汚染されることがある．

発展：グラフに穴があく

ノート

ここから先は 発展（必修ではない）． NaN が figure にどう現れるかを見たい人向けである．

次の有理式を考える．

\[ y = \frac{x^3+8}{x^3+3x^2-4x-12} \]

分母は \(x = -3,\; -2,\; 2\) で \(0\) になる．だから，この3点で不連続に なりうる．

重要予測しよう（L1）

\(x = -2\) の近くで，グラフはどうなっているだろうか． ほかの2点（\(x = -3\) と \(x = 2\)）と同じように見えるだろうか．

using Plots
xs = -4:0.01:4
ps = xs.^3 .+ 8                        # numerator
qs = xs.^3 .+ 3xs.^2 .- 4xs .- 12      # denominator
ys = ps ./ qs
plot(xs, ys, ylims=(-10, 10))

\(x = -3\) と \(x = 2\) では値が大きく振れるが，\(x = -2\) では何も起きていないように見える． 実際，その1点だけ値が NaN になっている．

[ps[findfirst(==(-2.0), xs)], qs[findfirst(==(-2.0), xs)], ys[findfirst(==(-2.0), xs)]]
3-element Vector{Float64}:
   0.0
   0.0
 NaN

分子も \(x = -2\) で \(0\) になるので，計算は 0/0 になり NaN が返る． plot は NaN の点を飛ばして描くので，そこに 穴があく（線が途切れる）．

分子と分母は，どちらも \((x+2)\) で割り切れる．

\[ \frac{x^3+8}{x^3+3x^2-4x-12} = \frac{x^2-2x+4}{(x+3)(x-2)} \]

約分した式で描き，もとのグラフと重ねてみる．

zs = (xs.^2 .- 2xs .+ 4) ./ ((xs .+ 3) .* (xs .- 2))
plot(xs, ys, ylims=(-10, 10), label="original")
plot!(xs, zs, label="reduced")

2本は \(x = -2\) を除いて 完全に重なる． 約分した式は \(x = -2\) でも値をもつ（\((4+4+4)/((1)(-4)) = -3\)）．

zs[findfirst(==(-2.0), xs)]            # the reduced form has a value here
-3.0

数学では \(x = -2\) は 除去可能な特異点 で，極限は \(-3\) である． しかし計算機は 0/0 を NaN としか答えない． 数学的に等しい式でも，書き方によって計算できたりできなかったりする（約分の前と後では，\(x=-2\) での定義のしかたが違う）．

今回のまとめ

  • 浮動小数点は有限の有効数字（Float64 は約10進15〜16桁）．表せない数は 丸められる（0.1 がそうだった）．
  • 情報落ち：桁違いの数を足すと小さい方が消える（1e16 + 1 == 1e16 が true）．
  • 桁落ち：近い数を引くと有効数字が消える（(1e16 + 1) - 1e16 が 0.0）．
  • 数値微分の U字：h を小さくしすぎると桁落ちで悪化．理論と実測の食い違いは 厳密値との差で暴く（L3）．
  • 小数の比較は == ではなく ≈（isapprox）．第6回の 0.1 + 0.2 == 0.3 はこれで説明がつく．
  • NaN は自分自身とも等しくない（NaN == NaN は false，判定は isnan）．Inf - Inf は NaN．
  • 整数（第9回）も小数（第10回）も 有限のビットの世界．計算機の数 ≠ 数学の数．

ヒント練習
  1. 0.1 + 0.2 == 0.3 が false になる理由を，「有限の有効数字」「丸め」という言葉を使って一文で説明せよ．
  2. (1e16 + 1) - 1e16 が 0.0 になる理由を，「情報落ち」「桁落ち」を区別して説明せよ．
  3. f(x) = sin(x) の x = 1 での数値微分を，いくつかの h で計算せよ．厳密値は cos(1) である．誤差が U字になる h の範囲を探し，最良の h を報告せよ．
  4. ふたつの小数 a，b が「十分近いか」を == で調べてしまっている誤ったコードを想定し，正しく直せ（直し方は一つではない）．
